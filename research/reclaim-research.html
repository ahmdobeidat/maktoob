Eligibility Criteria (what's scored)

01 · Open Source

OSI-approved license (MIT, GPLv3, Apache 2.0).

02 · Real Problem, Real Users

Must name the problem, who faces it, why existing solutions fall short.

03 · Practicality

Compatible with existing workflows — sync/bridge, don't force migration.

04 · Realistic Scope

One specific problem, not an entire platform. Must be maintainable post-event.

05 · User Ownership & Privacy

Data portability, transparency, privacy by design.

06 · Extensibility

APIs, webhooks, plugin systems, CLI, import/export formats.

07 · AI Usage

AI-assisted is fine. "AI slop" — unmaintainable AI-generated code — is penalized/disqualified.

⚠ Disqualifiers

Buzzwords w/o substance, vague problem statement, unrealistic scope, privacy violations, AI slop.

Judging patterns that repeat across every event studied

  • Completeness beats ambition, universally. Every winner citation used words like "complete," "well-documented," "polished." No half-built ambitious entry placed anywhere, in any year.
  • A working demo is non-negotiable. No event in this space rewards a deck over a running build.
  • Novelty is a tiebreaker on top of completeness — not a substitute for it. You need real polish, real novelty, or ideally both. Neither alone at a mediocre level wins (see Serenade).
  • Narrow real pain point > ambitious platform, with zero exceptions found. Every traceable winner across every event solved one specific, small, relatable problem.
  • OSS-maintainer judges pattern-match against their own project's origin story. RSS-Bridge, matterbridge, Syncthing, nchat all began as one maintainer scratching one specific itch — not "alternative to a whole company."
  • Standards-based interoperability is explicitly rewarded (Wroclaw-Transit / GTFS) — directly parallels Reclaim's own "extensibility" criterion.
  • Visible incremental commits during the event read as authenticity — directly relevant to the "AI slop" disqualifier; maintainers will likely check git history.
Bottom line: pick one narrow lock-in seam real Jordanian/Arabic-speaking users hit today, bridge or replace it (not rebuild the whole thing), ship a working self-hostable demo with clean docs and live commit history, expose one clean extension point. Favor "boring and complete" over "clever and half-built."
05 · Idea Catalog

All Winnable Ideas, By Track

Every idea below is shaped to match the judging patterns above: one narrow seam, one clear inspiration lineage, a concrete "why" tied to the eligibility criteria.

1

UX & Accessibility / Grandma-Friendly

No worked example cited by JOSA — wide open, but riskier to judge without a precedent to anchor to.
Grandma-Mode Front-End for Matrix or Pixelfed
inspo: Pixelfed / Matrix protocol
Why: strips device-linking, backup-phrase and instance-picking jargon down to a 3-tap flow. Satisfies "real problem, real users" directly — elderly users leaving WhatsApp/Facebook is a genuine, nameable pain point, and the scope is bounded (a UX layer, not a new protocol).
Single-Button "Send Photo to Family" Client
inspo: Nextcloud / Pixelfed backend
Why: voice-first or one-tap client on top of an existing open backend. The entire project is the UX simplification, keeping scope realistic while still being "extensible" (thin client on a documented API).
Fediverse Onboarding Wizard
inspo: Pixelfed / Mastodon instance-picker pain
Why: collapses the "which server do I even join" decision into a guided 3-step flow. Directly attacks the #1 known adoption blocker for federated alternatives — very demoable, very bounded.
2

Open Infrastructure Tooling

YunoHost's shape: package and wrap complexity, don't reinvent the underlying service.
One-Command "Leave Big Tech" Bundle
inspo: YunoHost
Why: bundles 2–3 open alternatives (Pixelfed + Syncthing + Matrix) behind a single YunoHost-style SSO login. Directly mirrors the single cited example for this track, which lowers judging risk while still being a real, complete, self-contained deliverable.
OAuth/SSO Proxy for Self-Hosted Apps
inspo: YunoHost's SSOWAT layer
Why: lets self-hosted open apps keep "login with Google" convenience while data lives outside Google. A narrow, single-seam bridge for identity specifically — very realistic scope, satisfies "practicality" (works with existing workflows).
Federated-Service Bootstrap Tool
inspo: YunoHost packaging model
Why: spins up a minimal ActivityPub/Matrix homeserver pre-wired with backups, TLS and monitoring. Scoped narrowly to just federation servers rather than "all of self-hosting" — avoids the "unrealistic scope" disqualifier.
3

Communication Freedom / Interoperability & Bridges

The dominant pattern in JOSA's own inspiration set (3 of 6 projects) — highest precedent, also highest expected competition.
WhatsApp Order Bridge for Small Jordanian Businesses
inspo: matterbridge (adapter shape)
Why: cafes, home bakers and small shops in Jordan run their entire order flow through raw WhatsApp DMs — no inventory, no tracking, but customers will never migrate off WhatsApp. Bridge incoming WhatsApp Business messages into a small self-hosted structured order dashboard: business gets data ownership, customer changes nothing. Hyper-local, narrow, standards-based output (webhook), trivially demoable live on stage, and matches almost every eligibility bullet at once (real users, no forced migration, realistic scope, ownership/privacy since data lands on their own DB). This is the strongest single candidate researched.
matterbridge Gap-Filler
inspo: matterbridge directly
Why: matterbridge covers ~15 platforms already; find what's genuinely missing (Instagram DMs, a voice-note-specific bridge) and build only that adapter. Risk: competing directly against a mature, polished existing OSS project on its own turf.
RSS-Bridge Generalized to Structured Webhooks
inspo: RSS-Bridge
Why: same per-source adapter pattern, applied beyond RSS — turn any closed app's public surface (App Store reviews, delivery-app order tracking) into a structured feed/webhook. Directly satisfies "extensibility."
Unified Inbox TUI
inspo: nchat
Why: nchat-style single terminal inbox unifying SMS (via local Android bridge) + email + Matrix. Appeals directly to the maintainer-judge persona (a power-user tool solving their own itch), lower mainstream "real users" breadth than the WhatsApp idea above.
4

Local-First & Data Ownership

Syncthing + Pixelfed's shape: no lock-in, portable data, zero central point of control.
"Migrate Me" Universal Import Tool
inspo: Pixelfed (portability) + Syncthing (transport)
Why: ingests a Google Takeout / Instagram export / WhatsApp chat export and auto-imports it into the matching open alternative (Pixelfed, Matrix, a Syncthing folder). Closes the "here's your zip file, good luck" gap nobody currently solves — directly attacks "real problem, real users" and "user ownership & privacy" better than a pure bridge does.
Syncthing-Based Continuous Vendor-Lock Escape
inspo: Syncthing directly
Why: auto-mirrors WhatsApp media / Google Photos exports continuously into a self-hosted folder — "your own iCloud" framing for people actively leaving Apple/Google. Narrow, ongoing (not one-shot), demoable as a live sync.
Local-First Companion for Pixelfed/Mastodon
inspo: Syncthing + Pixelfed combined
Why: caches your own posts/photos locally via Syncthing so you always have an offline personal archive independent of instance uptime. Literally combines two of JOSA's own cited inspirations — strong pattern-match for maintainer judges.
06 · Recommendation

Final Call

Recommended track & idea: Track 3 — WhatsApp Order Bridge for Small Jordanian Businesses.

Every comparable event studied converges on the same shape: a narrow, real, boring pain point, solved by bridging or replacing one specific lock-in seam, shipped as a working self-hostable demo with clean, documented code — not an ambitious platform, not a slide deck. JOSA's own cited inspirations are all single-maintainer projects born from one person's specific frustration with one specific proprietary chokepoint, and the judges are the kind of people who wrote projects exactly like that.

The WhatsApp order bridge fits that shape almost exactly: it's hyper-local (small businesses across Jordan genuinely run on raw WhatsApp DMs today), it doesn't ask anyone to migrate off WhatsApp, it's trivially demoable live (send a message on stage, watch a structured order appear in an open dashboard), and it satisfies nearly every eligibility bullet at once — real users, practicality, realistic scope, ownership/privacy, and a clean extension point (webhook out to any tool).

Execution checklist for the win condition

  • Ship visible, incremental git commits throughout the hacking period — judges are maintainers, they will check history, and this is the direct counter to the "AI slop" disqualifier.
  • Write real docs: problem statement, target user, install instructions, one architecture diagram.
  • Expose one clean extension point (webhook or minimal REST API) to explicitly satisfy "extensibility."
  • Keep scope to one business type, one message flow (orders in, structured record out) — resist adding inventory/payments/analytics before the core loop is rock-solid.
  • Demo live with a real phone sending a real WhatsApp message — no pre-recorded video, no slide-driven pitch.

Fallback options

If team skills don't line up with WhatsApp Business API integration in the time window, the next-best picks in order are: "Migrate Me" Universal Import Tool (Track 4 — best eligibility-criteria fit after the top pick) and Grandma-Mode Front-End (Track 1 — least competitive track, no precedent pressure).
